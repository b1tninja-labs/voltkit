# Scope

`voltkit` is a read client. It talks ELM327 to a loopback TCP peer, a Windows COM port, or an
OBDLink MX opened natively over the host Bluetooth radio.

- Do not send `$27`, a seed, or a key. `classify` refuses service `27` before the socket write.
- Do not add a write service (`$2E`, `$2F`, `$31`, `$11`, `$14`, `$34`–`$37`, `$85`).
- Do not add a VIN literal. The check-digit test uses the worked example in the GM filings
  `gm-vin-2016` through `gm-vin-2019`, read through `primarysource vin`. The Volt card is on
  every filing. The Bolt EV card starts in 2017. Do not copy a vehicle number into the tree.
- voltkit opens the host Bluetooth radio to reach a BLE OBDLink, including an MX that advertises the FFF0 serial service, natively and in-process. It links the `dangle` BLE library (the `ble` feature, Windows-gated like `vcx`): the wizard scans with `dangle::scan_advertisers`, and when the operator selects an MX, `voltkit` opens it with `dangle::connect(address, &SerialConfig::default())` and drives the ELM327 session over the returned byte pipe — no process is spawned and no TCP socket is used for the native BLE path. The owner authorized this over an earlier "do not add Bluetooth" rule, now that `dangle` exposes a BLE library crate (it was bin-only before). What stays fixed: `dangle` is a dumb byte pipe (no write or program path crosses it), and `unsafe` is forbidden in voltkit even though the radio is WinRT. A native host-OS BLE backend that drops `dangle` entirely (voltkit's own WinRT BLE) remains a possible future follow-up, not something to add now. The session and gauge commands stay on loopback. `voltkit lab` starts `fakeobd serve --listen 127.0.0.1:35000` and dials that address, or, with the `lab` feature, serves that bench in-process from the `fakeobd` library. `VOLTKIT_LAB_PEER` names the binary when it is not `fakeobd` on `PATH`. That command does not open a serial port or a Bluetooth radio. `voltkit bench` is the optional bring-the-bridge path: it starts the `dangle --name OBDLink` TCP bridge and dials that same address (for example to reach the radio from an emulator). The `dangle` README default for `--listen` is `127.0.0.1:35000`, so the command does not pass a listen flag. `VOLTKIT_BENCH_PEER` names the binary when it is not `dangle` on `PATH`. That command does not open a serial port, a Bluetooth radio, or a vehicle from voltkit itself. `voltkit profile` is the capture: it dials the TCP address the operator passes, on Windows opens the COM port they pass, or opens a `ble:<address>` dongle over the host radio. `--set` and `--range` choose which reads, and the range span is at most 256. `voltkit wizard` detects the adapters present, lets the operator select one instead of typing a COM port, asks which capture to run, and auto-writes the profile outside the repository. In a terminal that selection and question are a full-screen UI; a pipe keeps the line prompts (typed address). It still sends only reads.
- The adapters are detected, not invented: Windows COM ports come from `serialport::available_ports` with their friendly USB name; a VCX-NANO is identified by vcxtoolkit's `open_usb` + GetInfo doctor (a device query, never a vehicle read — the live `collect` stays gated in vcxtoolkit); MX devices come from `dangle::scan_advertisers` over the host radio (the serial-service advertisers). The capture path is ELM327 over TCP, over a Windows COM port, or over native host-radio BLE.
- The wizard is a two-phase, two-adapter flow, because the MX and the VCX-NANO collect different halves. Phase 1 (an ELM327-class adapter — MX over BLE, a COM port, or a Wi-Fi socket) is the read-only `$1A`/`$22` module clone to a fakeobd profile. Phase 2 (the VCX-NANO over USB) is the SPS / programming-data collect the ELM327 cannot reach. **Phase 2 runs the live read (owner-ungated, 2026-11-22).** The wizard's Phase 2 lets the operator CHOOSE the backend and runs the real read-only read (`$3E` TesterPresent, then the `$1A` identity DIDs) — it does **not** write a gated skeleton. The two backends are spawned as sibling tools, never reimplemented in voltkit: **native** runs our own `gmdiag vcx-read` (next to `voltkit.exe`), and **vendor** runs `vcx-vendor-read` (our `vcikit-j2534` loader driving VXDIAG's `VCXPT32.dll`, in `vxdiag-j2534\`). Native is first-class; the vendor path is the "read no matter what" backup. voltkit still owns no VCX decode of its own: it shells the engine (per the stack's ARCHITECTURE: voltkit → gmdiag) and shows its output. Do not copy spskit's controller rule table (device ids, request methods) into voltkit, and keep the read read-only ($3E/$1A only, never $27). The old gated-skeleton `stage::stage` path stays in the lib but is no longer wired into the wizard.
- Peer dependencies are optional Cargo features. `vcx` and `ble` are on by default but Windows-gated: the `vcxtoolkit` and `dangle` dependencies sit under `[target.'cfg(windows)'.dependencies]` and every use is `#[cfg(all(windows, feature = "vcx"))]` / `#[cfg(all(windows, feature = "ble"))]`, so the Linux build and a Windows build without the feature carry nothing and fall back gracefully (a "built without BLE support" message, like `vcx`). `lab` (off by default) links the `fakeobd` library for the in-process bench. voltkit links `dangle`'s BLE **library** (the `ble` feature) but does not link `dangle`'s **binary** (it is spawned for `voltkit bench`) or `spskit`; the handoff to those processes stays a TCP address, a profile file, or a saved module read. Do not add a `PassThru*` export or a `PassThruSupport.04.04` writer, and do not implement a registered J2534 pass-through: SAE J2534 is not in primarysource, so it stays a greyed, unbuilt option.
- `ATSP6` means ELM protocol 6 (ISO 15765-4 CAN, 11-bit, 500 kbaud). Do not describe it as
  ISO 15765-2.
- Scan headers come from the 2026-11-14 trial. Do not invent a response id for `621`.

`cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test`, and
`cargo doc --no-deps` pass before a change is done, and the default build builds on both
Ubuntu and Windows (the `vcx` and `ble` dependencies are Windows-gated, so the Linux default
build needs only `udskit`). `unsafe` is forbidden. No dependencies without a reason in the commit
message; the optional `vcx`/`ble`/`lab` features and their deps are documented in `Cargo.toml`.
`publish = false` stays. A release is a GitHub Release from a `v*.*.*` tag. It is not a crates.io
publish.
