# Scope

`voltkit` is a read client. It talks ELM327-over-TCP to a loopback peer.

- Do not send `$27`, a seed, or a key. `classify` refuses service `27` before the socket write.
- Do not add a write service (`$2E`, `$2F`, `$31`, `$11`, `$14`, `$34`–`$37`, `$85`).
- Do not add a VIN literal. The check-digit test uses the worked example in the GM filings
  `gm-vin-2016` through `gm-vin-2019`, read through `primarysource vin`. The Volt card is on
  every filing. The Bolt EV card starts in 2017. Do not copy a vehicle number into the tree.
- voltkit does not open a Bluetooth radio or a serial port for BLE itself. A BLE OBDLink, including an MX that advertises the FFF0 serial service, is reached through the `obd-bridge` process, which puts the same TCP socket in front of the radio. The wizard manages that process under the hood: when the operator selects an MX, `voltkit` spawns `obd-bridge --name OBDLink`, waits for its listen line, and captures as the one TCP client. The owner authorized this over an earlier "do not add Bluetooth" rule; what stays fixed is that the radio is opened by `obd-bridge`, not by voltkit. Native host-OS BLE inside voltkit (dropping the obd-bridge hop) is a deferred follow-up, and needs obd-bridge to expose a BLE library crate (it is bin-only today) or voltkit's own WinRT BLE. The session and gauge commands stay on loopback. `voltkit lab` starts `fakeobd serve --listen 127.0.0.1:35000` and dials that address, or, with the `lab` feature, serves that bench in-process from the `fakeobd` library. `VOLTKIT_LAB_PEER` names the binary when it is not `fakeobd` on `PATH`. That command does not open a serial port or a Bluetooth radio. `voltkit bench` starts `obd-bridge --name OBDLink` and dials that same address. The obd-bridge README default for `--listen` is `127.0.0.1:35000`, so the command does not pass a listen flag. `VOLTKIT_BENCH_PEER` names the binary when it is not `obd-bridge` on `PATH`. That command does not open a serial port, a Bluetooth radio, or a vehicle. `voltkit profile` is the capture: it dials the TCP address the operator passes, and on Windows it opens the COM port they pass. `--set` and `--range` choose which reads, and the range span is at most 256. `voltkit wizard` detects the adapters present, lets the operator select one instead of typing a COM port, asks which capture to run, and auto-writes the profile outside the repository. In a terminal that selection and question are a full-screen UI; a pipe keeps the line prompts (typed address). It still sends only reads.
- The adapters are detected, not invented: Windows COM ports come from `serialport::available_ports` with their friendly USB name; a VCX-NANO is identified by vcxtoolkit's `open_usb` + GetInfo doctor (a device query, never a vehicle read — the live `collect` stays gated in vcxtoolkit); MX devices come from parsing `obd-bridge scan`. The capture path is ELM327 over TCP, over a Windows COM port, or over the managed obd-bridge.
- The wizard is a two-phase, two-adapter flow, because the MX and the VCX-NANO collect different halves. Phase 1 (an ELM327-class adapter — MX over BLE, a COM port, or a Wi-Fi socket) is the read-only `$1A`/`$22` module clone to a fakeobd profile. Phase 2 (the VCX-NANO over USB) is the SPS / programming-data collect the ELM327 cannot reach. Phase 2 is held: the wizard's Phase 2 runs only the SAFE doctor (GetInfo, no vehicle channel) and writes a gated spskit-compatible skeleton of the read (the `parts`/`hardware`/VIN DIDs with empty values), marked gated. Do not unhold or send the live SPS read, do not add the `VCX_PRO_Recv` live decode, and do not copy spskit's controller rule table (device ids, request methods) into voltkit; the skeleton uses only the vehicle-derived DIDs voltkit already models, and spskit maps those to its controllers.
- Peer dependencies are optional Cargo features, off the lean default path. `vcx` (on by default, but the `vcxtoolkit` dependency is under `[target.'cfg(windows)'.dependencies]` and every use is `#[cfg(all(windows, feature = "vcx"))]`, so the Linux build and a Windows build without the feature carry nothing and fall back gracefully). `lab` (off by default) links the `fakeobd` library for the in-process bench. Do not link `obd-bridge` (it is bin-only; voltkit spawns it) or `spskit`; the handoff to those stays a TCP address, a profile file, or a saved module read. Do not add a `PassThru*` export or a `PassThruSupport.04.04` writer, and do not implement a registered J2534 pass-through: SAE J2534 is not in primarysource, so it stays a greyed, unbuilt option.
- `ATSP6` means ELM protocol 6 (ISO 15765-4 CAN, 11-bit, 500 kbaud). Do not describe it as
  ISO 15765-2.
- Scan headers come from the 2026-11-14 trial. Do not invent a response id for `621`.

`cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test`, and
`cargo doc --no-deps` pass before a change is done, and the default build builds on both
Ubuntu and Windows (the `vcx` dependency is Windows-gated, so the Linux default build needs
only `udskit`). `unsafe` is forbidden. No dependencies without a reason in the commit message;
the optional `vcx`/`lab` features and their deps are documented in `Cargo.toml`. `publish =
false` stays. A release is a GitHub Release from a `v*.*.*` tag. It is not a crates.io publish.
